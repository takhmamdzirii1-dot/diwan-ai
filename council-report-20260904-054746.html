LLM Council · Architecture decision

Production-grade localization for VANTRA

What is the best architecture for VANTRA’s public marketing experience, considering conversion, SEO, Arabic RTL, performance, maintainability, multi-machine development, and future growth?

Chairman verdict

Adopt next-intl, narrowly scoped to public marketing.

Architecture: explicit /fr, /ar, and /en routes; a cache-safe root resolver; separate marketing and Studio root layouts; server-loaded active-locale dictionaries; shared components; localized SEO; targeted RTL handling.

Where the Council agrees

  • Resolve only / using vantra_locale → Accept-Language → French.
  • Never redirect away from an explicit supported locale route.
  • Use a server-readable SameSite=Lax cookie; localStorage is unnecessary.
  • Render Arabic lang="ar" dir="rtl" in the initial HTML and isolate LTR brand/model names.
  • Keep one shared component system and load only the active locale’s messages.
  • Keep Studio outside today’s localization scope while preserving a future path.
  • Use localized metadata, self-canonicals, reciprocal hreflang, x-default, and localized sitemap entries.
  • Transcreate sales copy and do not invent product facts.

Where the Council clashes

The only material disagreement is native App Router localization versus next-intl. The native proposal avoids one dependency, but the majority concluded it would make VANTRA maintain its own validation, navigation, client/server message delivery, missing-key behavior, formatting, metadata, and future expansion layer.

Blind spots caught in peer review

Cache correctness at the root; the App Router document-layout boundary; dictionary parity and fresh-clone testing; separating verified facts from persuasive copy; analytics parity; and a deliberate French/Arabic review workflow.

Recommendation

Use next-intl for the localized marketing route group, keep Studio in a separate unlocalized root, statically render explicit locale pages, and reserve request-based negotiation for /. The dependency and full document navigation at the marketing-to-Studio boundary are acceptable tradeoffs for correct initial document semantics and lower long-term maintenance risk.

The one thing to do first

Establish and test the locale routing and document boundary before migrating copy.

Advisor detail

The Contrarian

The “lightweight native” option has a likely fatal flaw: it looks simple only while VANTRA has one page. Hardcoded dictionary access, hand-built locale navigation, metadata alternates, cookie negotiation, missing-key handling, and mixed server/client message delivery quickly become an undocumented internal framework. Use next-intl, narrowly scoped to public marketing, and implement routing/layout first.

The First Principles Thinker

Choose native App Router localization. Three static marketing dictionaries, deterministic routing, metadata, and directionality do not inherently require runtime translation machinery. Use a validated locale segment, localized HTML-owning layout, separate Studio boundary, root-only resolver, one cookie, and active typed dictionary.

The Expansionist

Adopt next-intl. Its routing, navigation, message, pluralization, formatting, and future Studio leverage justify it. Keep explicit locale routes, server-loaded messages, shared components, correct initial direction, localized SEO, and a durable cookie.

The Outsider

Use next-intl because client-heavy shared components and future expansion make custom infrastructure deceptively costly. Keep explicit routes, a root-only resolver, one cookie, correct document attributes, LTR token isolation, self-canonicals, hreflang, x-default, and sitemap entries.

The Executor

Use next-intl as the fastest safe production path. Create routing/request configuration and a proxy, explicit locale routes, one active server dictionary, shared components, correct RTL and SEO, and root-resolution tests. Do not add localStorage.
